# Spec 문서 리뷰

사용자가 spec 문서 리뷰를 요청하면 아래 절차를 수행한다. 이 스킬은 `spec` 스킬이 만든 문서(EARS 표기, `specs/_baseline.md`의 `G-`/`D-` 참조, Correctness Properties, `_Requirements:` 역참조, 완료 조건, `[ ]`/`[-]`/`[~]`/`[x]` 체크박스 상태)를 전제로 리뷰한다 — 이 컨벤션을 따르지 않는 스펙 문서(다른 도구가 만든 레거시 스펙 등)에는 적용하지 않는다.

## 절차

1. 리뷰 대상 파일을 확인한다 (requirements.md, design.md, tasks.md 중 하나 이상 — 사용자가 특정하지 않으면 해당 스펙 디렉토리에 존재하는 파일 전부).
2. `Agent`로 `spec-reviewer`를 foreground(`run_in_background: false`)로 호출해 대상 파일(들)의 검토를 위임한다 — 이 에이전트가 [리뷰 체크리스트](references/REVIEW-CHECKLIST.md) 적용, `specs/_baseline.md` 대조, 심각도 판정(아래 분류 참고), 출력 형식 구성까지 전부 수행한다. 체크리스트 로직의 원본은 `REVIEW-CHECKLIST.md` 하나뿐이므로 메인 스레드가 별도로 다시 체크리스트를 적용하지 않는다.
3. 받은 보고를 그대로 사용자에게 전달한다.

## 심각도 분류

| 등급 | 기준 | 판정 영향 |
|------|------|-----------|
| 🚫 BLOCK | 구현 시 잘못된 결과를 낳는 문제 (AC 조건 누락, What/How 혼재, 범위 불일치, 요구사항 역추적 누락, 완료 조건 누락, 기술적 실현 불가) | 수정 필수 |
| ⚠️ WARN | 구현 가능하나 모호성·중복·비일관성 존재 (비한정 표현, 경계 조건 미흡, 용어 불일치, 설계 근거 부족) | 수정 권장 |
| ℹ️ INFO | 품질 향상 제안이나 구현에 영향 없음 (표현 다듬기, 주석 보충) | 판정에 미반영 |

## 판정 규칙

- BLOCK 1건 이상: **수정 필수** (다음 단계 진행 불가로 간주)
- BLOCK 없음 + WARN 존재: **수정 권장** (사용자 판단에 따라 진행 가능)
- WARN·BLOCK 없음: **리뷰 통과**

## 출력 형식

```
## 리뷰 결과: {파일명}

### 통과 항목
- (문제없는 항목 나열)

### 지적 사항
| # | 심각도 | 항목 | 위치 | 내용 | 수정 제안 |
|---|--------|------|------|------|-----------|
| 1 | 🚫 BLOCK | ... | ... | ... | ... |

### 종합 판정
(수정 필수 / 수정 권장 / 리뷰 통과)
```

여러 파일을 리뷰하면 파일별로 위 블록을 반복한 뒤, 맨 끝에 스펙 전체의 종합 판정(가장 심각한 등급 기준)을 한 줄 추가한다.

## Gotchas

- **지적만 하고 고치지 않는다.** 이 스킬은 리뷰 결과를 보고하는 것으로 끝난다 — 발견한 문제를 자동으로 수정하지 않는다. `spec-reviewer` 에이전트에는 애초에 Write/Edit 도구가 없어서 이 계약이 구조적으로 보장된다. 사용자가 수정을 요청하면 `spec` 스킬로 넘어가 정상 승인 절차(사용자 확인 후 반영)를 따른다.
- **완료된 스펙(마지막 태스크까지 `[x]`)도 리뷰할 수 있다.** 다만 그 결과로 발견된 문제를 그 스펙 문서에 바로 반영하지 않는다 — `spec` 스킬의 "완료된 스펙은 닫힌 기록" 규칙에 따라 새 스펙에서 다룬다.
- **`_Requirements:`가 가리키는 번호가 실제로 requirements.md에 있는지는 파일을 열어 직접 대조한다** — 번호가 그럴듯해 보인다고 통과시키지 않는다.
