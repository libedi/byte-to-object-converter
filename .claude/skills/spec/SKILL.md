# Spec 문서 작성

이 스킬은 두 종류의 스펙 문서를 다룬다.

- **Feature spec** (`specs/<spec-name>/`) — 특정 시점의 요구사항(기능/리팩토링 등)을 requirements.md(무엇을) → design.md(어떻게) → tasks.md(어떤 순서로) 3단계로 정리한 문서. SDD(스펙 기반 개발)의 실제 대상이다 — tasks.md를 따라 구현한다. 완료되면 편집하지 않는 닫힌 기록이 된다.
- **Baseline spec** (`specs/_baseline.md`) — 프로젝트의 현재 상태를 나타내는 정본 문서. **SDD 대상이 아니다** — 이 문서 자체에 대한 requirements.md/design.md/tasks.md 사이클은 만들지 않는다. feature spec들이 반복해서 정의하지 않도록 프로젝트 전역의 규칙·결정·용어를 모아두고, 각 feature spec의 가드레일 역할을 한다. 독립적으로 새로 시작하지 않는다 — 항상 feature spec의 마지막 태스크(4단계 참고)를 통해서만 만들어지거나 갱신된다.

업무 기능뿐 아니라 리팩토링·빌드 시스템 개선 같은 기술 요건에도 동일하게 적용한다 — 그 경우 User Story의 역할은 "개발자"/"메인테이너"처럼 한글로 쓰면 된다 (언어 규칙 참고).

## 언제 이 워크플로우 전체를 쓸지

여러 파일에 걸친 변경, 되돌리기 어려운 결정(빌드 시스템 전환, public API 변경 등), 또는 사용자가 명시적으로 스펙을 요청한 경우에 쓴다. 사소한 버그 수정이나 한 파일짜리 변경에는 쓰지 않는다 — 그런 작업은 그냥 바로 구현한다.

## 3단계 워크플로우

각 단계는 **이전 단계에 대한 사용자 승인 없이는 시작하지 않는다.** "LGTM", "좋아", "진행해" 같은 명시적 승인을 받은 뒤에만 다음 파일을 작성한다. 사용자가 "질문 없이 한 번에 다 만들어줘"라고 명시적으로 요청한 경우에만 게이트를 건너뛰고 세 파일을 순서대로 한 번에 생성해도 된다.

### 1. 스펙 이름/위치 정하기

- 작업 내용에서 kebab-case 이름을 짓는다 (예: `dependency-plugin-modernization`).
- **디렉토리명 앞에 2자리 인덱스를 붙인다** (예: `01-dependency-plugin-modernization`) — `specs/`를 나열했을 때 생성 순서대로 정렬되게 하기 위함이다. `specs/` 아래 `NN-` 형식의 인덱스가 붙은 기존 디렉토리를 찾아 가장 큰 번호 다음 번호를 쓴다. 그런 디렉토리가 하나도 없으면 `01`부터 시작한다. `NN-` 접두사가 없는 예전 디렉토리(이 컨벤션 이전에 만들어진 스펙)는 번호 계산에서 무시하고 그대로 둔다 — 소급해서 이름을 바꾸지 않는다.
- 저장 위치는 저장소 루트의 `specs/<spec-name>/`(인덱스 포함). 없으면 새로 만든다.
- 인덱스를 뺀 kebab-case 이름 기준으로 이미 같은 스펙이 있으면 덮어쓰지 말고 사용자에게 갱신할지 새 이름을 쓸지 물어본다.
- `specs/_baseline.md`(프로젝트 전역 anchor 문서, baseline spec)가 있는지 확인한다. 있으면 읽어서 이번 스펙에 적용되는 전역 규칙·결정·용어를 파악해둔다 — requirements.md/design.md에 다시 옮겨 적지 않는다. 없다면 지금 만들 필요는 없다 — 이 스펙의 tasks.md 마지막 태스크("관련 문서 업데이트")에서 승격 대상이 있을 때 만든다. 단, `specs/` 아래 이미 완료된 다른 스펙이 있는데도 baseline이 없다면 드문 경우다 — 이전 스펙에서 승격할 게 정말 없었는지 의심해본다(프로젝트 차원 결정이 하나도 없는 경우는 드물다).

### 2. requirements.md 작성

`assets/requirements-template.md` 형식을 따른다.

- **What에만 집중한다.** 시스템이 무엇을 해야 하는가, 무엇을 만족해야 하는가만 쓴다. 특정 라이브러리·클래스 구조·알고리즘 같은 구현 방법은 여기 쓰지 않는다 — design.md의 몫이다. 대화 중 구현 방법이 먼저 나오면 기억해두었다가 design.md 단계에서 반영한다.
  - How가 새어 들어오는 흔한 형태(고전적인 "라이브러리/알고리즘"뿐이 아니다): 빌드 도구·프레임워크의 설정 키워드나 스코프 이름(예: Gradle의 `api`/`implementation`/`testImplementation`), 대안이 여러 개 있는데 그중 하나를 콕 집어 쓴 특정 API/클래스명(예: 폴백 구현으로 `java.lang.reflect`를 지목), 도구가 성공을 알리는 방식의 세부사항(예: `BUILD SUCCESSFUL` 문자열, 종료 코드 0 — 이런 "검증 방법"은 design.md의 Testing Strategy로 보낸다).
  - Acceptance Criteria를 다 쓴 뒤 한 문장씩 다시 훑으며 자가 점검한다: *이 표현을 지우거나 다른 구현으로 바꿔도 문장이 말하는 관찰 가능한 결과(무엇이 참이어야 하는가)가 그대로 유지되는가?* 그렇다면 그 표현은 How이니 관찰 가능한 결과 서술로 바꾼다. 유지되지 않는다면(그 이름 자체가 요구사항의 대상, 예: 버전 번호, 제거 대상 의존성 이름) 그대로 둔다.
- 대화 맥락에서 요구사항을 추출한다. 애매한 부분(엣지 케이스, 비기능 요구사항, 대상 범위)이 있어도 드래프트 중간에 끊고 되묻지 않는다 — 합리적으로 판단해서 쓰고, 판단이 명시적이지 않은 곳은 가정한 내용을 드러나게 적어둔다. 승인 단계에서 사용자가 검토하며 수정 요청을 하면 그때 반영한다. 핵심 스코프 자체가 불명확해서 드래프트를 시작할 수조차 없는 경우에만 먼저 묻는다.
- Acceptance Criteria는 반드시 EARS 표기법(아래 참고)으로 쓰고, `Requirement N` 안에서 `N.1`, `N.2` ...로 번호를 매긴다 — 이 번호가 design.md/tasks.md에서 역참조되는 유일한 앵커다.
- **Constraints는 이 스펙 한정 범위만 적는다.** "이렇게는 하지 마라" 류의 하드 룰이 나오면, 그게 이 작업에만 해당하는 범위 제한(예: "이번 스펙에서는 Gradle 버전을 안 건드린다")인지, 아니면 프로젝트 전역에 걸쳐 항상 성립해야 하는 것(예: "자격증명은 절대 커밋하지 않는다")인지 구분한다. 후자라면 이 스펙의 requirements.md에 넣지 말고, tasks.md를 작성할 때(4단계) 마지막 "관련 문서 업데이트" 태스크의 서브태스크로 `specs/_baseline.md` 승격을 반영할 후보로 남겨둔다. 전역 제약은 requirements.md에서 링크로만 참조한다.
- **Glossary도 전역/스펙 한정을 구분한다.** `specs/_baseline.md`에 전역 Glossary가 있으면 참조만 하고 다시 정의하지 않는다. 이 스펙에서만 쓰는 용어만 이 문서의 Glossary에 적는다. 다른 스펙에서도 반복될 법한 공통 용어라면 승격 후보로 남겨둔다.
- 작성 후 승인 요청 직전에 아래 "승인 전 자동 진단" 절차를 거친 뒤, 최종본과 자동 검토/수정 내역을 함께 사용자에게 보여주고 승인을 기다린다.

**승인 전 자동 진단 (requirements.md)**: `Agent`로 `spec-reviewer`를 foreground(`run_in_background: false`)로 호출해 방금 쓴 requirements.md를 검토시킨다. BLOCK/WARN이 있으면 **메인 스레드가 직접** 수정한다(대화 맥락에서 나온 내용이라 서브에이전트에 위임하지 않음) — INFO는 고치지 않고 그대로 둔다. 수정 후 `spec-reviewer`를 한 번 더 호출해 재검토한다(최대 1회 재시도). 그래도 BLOCK이 남으면 숨기지 않고 있는 그대로 사용자에게 보고한다. 승인 요청 시 무엇을 자동으로 찾아 고쳤는지, 남은 INFO 제안이 있다면 그것도 함께 제시한다.

### 3. design.md 작성

`assets/design-template.md` 형식을 따른다.

- **How에 집중한다.** 승인된 requirements.md의 요구사항 번호를 근거로, 그 What을 구현할 기술적 방법을 쓴다.
- 설계 결정의 근거는 중앙에 모아놓지 않는다. 자명하지 않은 선택(왜 이 라이브러리/패턴/구조를 골랐는가)이 있는 컴포넌트에만, 그 컴포넌트 설명 바로 아래에 짧게 남긴다. 모든 컴포넌트에 억지로 채우지 않는다.
- **`specs/_baseline.md`가 있으면 관련 항목의 준수 여부를 밝힌다.** 이 스펙과 관련된 `G-`(전역 규칙)/`D-`(결정 기록) 항목만 골라 나열하고, 각각 준수하는지 이탈하는지 명시한다 — 이탈이면 사유가 필수다. 관련 없는 항목까지 전부 나열하지 않는다. `assets/design-template.md`의 "Baseline Alignment" 섹션 참고.
- 다이어그램(mermaid)은 흐름이나 컴포넌트 관계가 글로만 설명하기 어려울 때만 넣는다 — 장식용으로 넣지 않는다.
- **Correctness Properties를 검토한다.** requirements.md의 각 Acceptance Criteria를 훑어, "임의의 입력에 대해 항상 성립해야 하는 보편적 속성"으로 표현 가능한 것이 있는지 판단한다. 이 검토 자체는 매번 한다. 다만 실제로 의미 있는 property가 없으면(정적 설정 검사, 외부 서비스 연동처럼 property로 표현해도 얻는 게 없는 경우) 억지로 만들지 않고 "왜 example-based test로 충분한지"를 한 줄로 기록한다. 있으면 `Property N` 형식으로 기록하고 관련 Requirement 번호를 `Validates: N.M`으로 남긴다. **Property를 실제로 태스크화할 때는 jqwik을 쓴다** — AutoParams(`@AutoSource`)는 무작위 예시 데이터를 생성할 뿐 shrinking을 지원하지 않아 진정한 property 검증에는 부족하다. 프로젝트에 jqwik 의존성이 아직 없으면 tasks.md에 추가 태스크를 포함한다.
- 초안 작성은 `Agent`로 `spec-executor`를 foreground(`run_in_background: false`)로 호출해 "design.md 초안 작성 모드"로 위임한다(spec 디렉토리 경로 전달). 입력이 승인된 requirements.md와 코드베이스뿐이라 대화 맥락 없이도 자기완결적으로 작업 가능하기 때문이다. 코드 탐색이 거의 필요 없는 순수 설정/문서 스펙이라면 메인 스레드가 직접 써도 무방하다.
- 초안이 나오면 아래 "승인 전 자동 진단(design.md/tasks.md 공통)" 절차를 거친 뒤, 최종본과 자동 검토/수정 내역을 함께 사용자에게 보여주고 승인을 기다린다.

**승인 전 자동 진단 (design.md/tasks.md 공통)**: `Agent`로 `spec-reviewer`를 foreground로 호출해 검토시킨다. BLOCK/WARN이 있으면 그 목록을 `Agent`로 `spec-executor`에게 "결함 수정 모드"로 전달해 고치게 한다(INFO는 건드리지 않음) — design.md/tasks.md는 입력이 파일로 자기완결적이라 `spec-executor`가 직접 수정해도 안전하다. 수정 후 `spec-reviewer`를 한 번 더 호출해 재검토한다(최대 1회 재시도). 그래도 BLOCK이 남으면 숨기지 않고 있는 그대로 사용자에게 보고한다. `spec-executor`가 수정 중 requirements.md 자체의 요구사항 갭을 발견해 플래그를 남겼다면, 메인 스레드가 그 갭을 requirements.md에 반영하고 사용자에게 재승인을 받은 뒤에야 다음 단계로 진행한다.

### 4. tasks.md 작성

`assets/tasks-template.md` 형식을 따른다.

- 체크박스 트리(`- [ ] 1.`, `- [ ] 1.1`)로 작업을 쪼갠다. **모든 리프 태스크는 끝에 `_Requirements: N.M, ..._`로 requirements.md의 항목 번호를 역참조해야 한다** — 이게 없으면 태스크가 어떤 요구사항을 충족하는지 추적할 수 없다.
- **모든 리프 태스크는 `_Requirements:` 줄 바로 위에 `**완료 조건:**`으로 관찰 가능한 완료 기준(Definition of Done)을 명시해야 한다.** `_Requirements:` 역참조는 "어떤 요구사항에 매핑되는가"만 보여줄 뿐 "언제 끝났다고 판단하는가"는 말해주지 않는다. 완료 조건은 실행 후 참/거짓으로 확인 가능해야 한다 — 특정 명령의 성공 종료, 특정 테스트의 통과, 특정 파일/산출물의 존재 등. "적절히 동작한다"처럼 주관적인 서술은 완료 조건이 아니다. Red→Green→Refactor 태스크는 "Green에서 통과시킨 테스트가 Refactor 이후에도 계속 통과"가, 검증(Step N 검증) 태스크는 "그 Step의 검증 명령어가 전부 성공 종료"가 곧 완료 조건이 되는 경우가 많다. `assets/tasks-template.md`의 각 태스크 예시 참고.
- 단계 사이에 "Checkpoint" 태스크를 넣어 사용자가 확인할 지점을 명시한다.
- **비즈니스 로직을 구현하는 태스크는 Red → Green → Refactor 순서로 하위 단계를 쪼갠다.** Red 단계의 테스트는 반드시 해당 태스크가 역참조하는 Acceptance Criteria나 Correctness Property에서 도출한다(테스트를 먼저 상상해서 만들지 않는다). 순수 설정/빌드/인프라 태스크에는 이 구조를 강제하지 않는다. `assets/tasks-template.md`의 예시 참고.
- **마지막 태스크는 항상 "관련 문서 업데이트"로 만든다 (생략 불가, Final Checkpoint 다음).** 판단은 지금(tasks.md 작성 시점) 끝낸다 — requirements.md/design.md가 이미 승인된 상태이므로 `references/spec-promotion-rules.md` 기준을 지금 적용해 승격 대상을 구체적으로 정한다. 갱신할 문서/항목별로 서브태스크를 만든다(예: "specs/_baseline.md에 G-3 추가", "CLAUDE.md의 X 절 갱신") — 개수는 0개(승격 대상 없음)부터 여러 개까지 스펙마다 다르다. 이 목록은 tasks.md 승인 때 함께 검토받으므로, **태스크 실행 시점에는 다시 판단하지 않고 목록대로 수행만 한다.** `assets/tasks-template.md`의 마지막 태스크 예시 참고.
- 초안 작성은 `Agent`로 `spec-executor`를 foreground로 호출해 "tasks.md 초안 작성 모드"로 위임한다(spec 디렉토리 경로 전달). 입력이 승인된 requirements.md와 design.md뿐이라 대화 맥락 없이도 자기완결적으로 작업 가능하기 때문이다.
- 초안이 나오면 "3. design.md 작성" 절의 "승인 전 자동 진단(design.md/tasks.md 공통)" 절차를 동일하게 거친 뒤, 최종본과 자동 검토/수정 내역을 함께 사용자에게 보여주고 승인을 기다린다.

## EARS 표기법 규칙

Acceptance Criteria는 아래 세 패턴만 사용한다. 자유 서술형 문장으로 쓰지 않는다.

- `THE <System> SHALL <behavior>` — 조건 없이 항상 성립해야 하는 요구사항
- `WHEN <condition/event> THE <System> SHALL <behavior>` — 특정 이벤트/조건에서 반응
- `IF <condition> THEN THE <System> SHALL <behavior>` — 예외/에러 케이스

`<System>`은 요구사항 문서 전체에서 일관된 이름을 쓴다 (예: "Build_System", "Converter"). 한 요구사항 안에 이 세 패턴이 섞여도 된다.

## 언어 규칙

스펙 문서는 구조를 나타내는 키워드만 영문으로 쓰고, 그 외 설명 내용은 전부 한글로 쓴다.

- **영문으로 쓰는 것**: 템플릿에 정의된 섹션 제목(Introduction, Requirements, Acceptance Criteria, Constraints, Glossary, Overview, Architecture, Components and Interfaces 등), EARS 키워드(`THE`/`SHALL`/`WHEN`/`IF`/`THEN`), User Story 형식 키워드(`As a`/`I want`/`so that`), `<System>` 식별자(예: `Build_System`), ID 접두사(`C-`/`G-`/`D-`), 기술 고유명사(라이브러리명·클래스명·파일 경로·버전 번호 등 코드/설정에 실제로 등장하는 이름).
- **한글로 쓰는 것**: 위 키워드 사이를 채우는 실제 내용 — User Story의 역할/능력/이익, Acceptance Criteria의 조건·동작 서술(`<condition/event>`, `<behavior>` 자리), 표 안의 설명, Notes, 그 외 모든 서술 문장.
- User Story는 `As a <역할>, I want <능력>, so that <이익>.` 형식의 영문 키워드는 그대로 두고, `<역할>`/`<능력>`/`<이익>` 자리만 한글로 채운다 — `assets/requirements-template.md`의 예시를 따른다.
- 이 규칙을 지키기 위해 이 프로젝트 밖의 다른 형식·다른 도구가 남긴 스펙 문서(레거시 스펙 디렉토리 등)를 참고하지 않는다 — 이 스킬의 지시와 현재 대화 맥락만으로 작성한다.

## 서식 규칙

한 문단(또는 리스트 항목 하나)은 파일 안에서 한 줄로 쓴다 — 일정 글자 수마다 임의로 개행하지 않는다. Markdown 렌더러는 문단 중간 개행을 공백으로 접기 때문에, 인위적인 개행은 뷰어에는 안 보이면서 원본 파일에서만 어색하게 끊긴 줄로 남는다. 실제로 별도 줄로 보여야 하는 경우(리스트 항목 구분, 표 행, 코드 블록, 의도적인 줄바꿈)에만 개행한다.

내용이 실제로 열거형(예: "(1) ... (2) ... (3) ...")이면 한 문단에 욱여넣지 말고 Markdown 리스트 문법(`-` 또는 `1.`)으로 항목마다 줄을 나눠 쓴다. 렌더링된 뷰어에서는 인라인 열거도 리스트처럼 보일 수 있지만, 원본 파일에서는 리스트 구조가 겉으로 드러나지 않아 항목을 추가·재배치하기 어렵고 diff도 지저분해진다.

## 실행 중 상태 갱신 (tasks.md)

tasks.md의 태스크는 다음 네 상태를 가진다. 표준 GFM은 `[ ]`/`[x]` 두 가지뿐이라 진행 상황을 다 담지 못하므로, 이 스킬에서 정한 자체 컨벤션이다.

- `[ ]` — 작성됨, 아직 실행 범위에 포함되지 않음 — tasks.md를 처음 쓸 때 모든 태스크는 이 상태로 시작한다.
- `[-]` — 대기(큐잉) — **실행을 시작할 때**, 이번 실행 범위에 포함되는 모든 미완료 태스크를 한 번에 `[ ]` → `[-]`로 일괄 마킹한다(범위 예: "전체 실행"이면 남은 태스크 전부, "태스크 1, 2만"이면 그 둘만 — 나머지는 `[ ]`로 그대로 둔다).
- `[~]` — 진행 중 — 지금 실제로 작업 중인 태스크. **해당 태스크를 시작하는 즉시** `[-]` → `[~]`로 개별 갱신한다.
- `[x]` — 완료 — 그 태스크의 **완료 조건**(tasks.md 참고)을 실제로 확인한 뒤 `[~]` → `[x]`로 개별 갱신한다.

전환 순서는 항상 `[ ]` → `[-]`(일괄, 실행 시작 시 한 번) → `[~]`(개별) → `[x]`(개별)다. `[-]`↔`[~]`↔`[x]` 개별 전환은 실제 작업 바로 앞/뒤 도구 호출로 하고, 몰아서 갱신하지 않는다.

**Checkpoint 태스크는 예외다.** 사용자 확인을 기다리는 동안은 `[~]`로 바꾸지 않고 `[-]`로 둔다 — 기다리는 것은 "진행 중"이 아니다. 확인을 받으면 바로 `[x]`로 갱신한다.

## Gotchas

- **요구사항 번호를 지어내지 않는다.** design.md나 tasks.md에서 참조하는 `N.M` 번호는 반드시 실제 requirements.md에 존재해야 한다. 새로 필요한 요구사항이 생기면 tasks.md를 쓰기 전에 requirements.md로 돌아가 추가하고 사용자에게 다시 승인받는다.
- **ID 접두사를 섞지 않는다.** `C-`는 이 스펙 한정 제약(requirements.md), `G-`는 전역 규칙(`_baseline.md`), `D-`는 전역 결정 기록(`_baseline.md`). 태스크의 `_Requirements: N.M_` 역참조와도 형식이 다르다.
- **모호한 용어는 Glossary에 정의한다.** "빠른 응답", "대용량 파일"처럼 구현마다 다르게 해석될 수 있는 표현이 나오면 EARS 문장에 그대로 쓰지 말고 Glossary에서 구체적 기준으로 정의한 뒤 인용한다.

## 완료 후

tasks.md까지 승인되면 스펙 문서 작성 자체는 끝이다. 실제 구현은 이 스킬의 범위가 아니다 — 사용자가 태스크 실행을 요청하면 tasks.md를 순서대로 따라가며 위의 상태 갱신 규율을 지키고, 각 Checkpoint에서 멈춰 확인받는다. 마지막 "관련 문서 업데이트" 태스크(4단계 참고)에서 Decision Log(`D-`) 항목을 추가할 때는 상세 근거를 다시 옮겨 적지 않는다 — 한 줄 요약과 이 스펙 design.md로의 링크만 남긴다. 상세 근거의 원본은 항상 그 결정을 처음 내린 스펙의 design.md다.

**리프 태스크 실행은 `spec-executor`에 위임한다.** 절차는 다음과 같다: (1) 실행 범위에 포함되는 미완료 태스크를 메인 스레드가 한 번에 `[ ]`→`[-]`로 일괄 마킹한다. (2) 리프 태스크 하나를 시작하기 직전, 메인 스레드가 그 태스크만 `[-]`→`[~]`로 개별 전환한다. (3) `Agent`로 `spec-executor`를 foreground로 호출해 "리프 태스크 실행 모드"로 그 태스크 번호를 위임한다 — 같은 스펙의 태스크를 연속으로 실행하는 동안은 `SendMessage`로 동일 인스턴스를 이어서 써서 콜드 스타트 비용을 줄이되, 세션 재시작 등으로 그 인스턴스에 다시 접근하지 못해도 새로 호출하면 파일에서 상태를 재구성하므로 정상 동작한다. (4) 에이전트의 보고를 받으면, 그 보고를 그대로 신뢰하지 않고 메인 스레드가 태스크의 `**완료 조건:**`을 직접 검증한다. (5) 검증되면 `[~]`→`[x]`로 개별 전환하고 사용자에게 진행 상황을 보고한다. **Checkpoint 태스크는 위임하지 않는다** — 에이전트는 사용자와 직접 대화할 채널이 없으므로 메인 스레드가 직접 확인을 받는다.

**완료된 스펙은 닫힌 기록이다.** 마지막 태스크까지 `[x]`가 되면 이 스펙은 더 이상 편집하지 않는다. 이후 새로운 요구사항이나 변경이 필요해지면 새 스펙을 만든다 — 관련이 있으면 새 스펙의 Introduction에서 이전 스펙을 언급한다. 아직 진행 중인 스펙(태스크가 전부 `[x]`는 아닌 상태)은 정상적인 승인 절차를 거쳐 requirements.md/design.md/tasks.md를 갱신할 수 있다 — 이때도 새 Requirement/AC는 항상 기존 번호 뒤에 추가한다(끼워넣지 않는다).
