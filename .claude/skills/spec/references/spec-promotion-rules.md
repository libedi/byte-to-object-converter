# Spec Promotion Rules

feature spec에서 나온 제약/결정/용어를 `specs/_baseline.md`로 승격할지 판단하는 기준이다. `spec` 스킬이 tasks.md를 작성하는 시점(4단계)에 이 문서를 읽고 판단을 끝낸다 — requirements.md/design.md가 이미 승인된 상태이므로 이때 판단해도 늦지 않고, 이후 태스크 실행 시점에는 이미 정해진 목록을 그대로 수행하기만 하면 되어 중간에 판단을 다시 할 필요가 없다.

## 승격 기준

아래 중 하나 이상 해당하면 승격 후보다.

1. **재사용성** — 이 결정/제약이 이번 스펙 하나의 구현 디테일이 아니라, 앞으로 다른 스펙도 지켜야 하는 원칙인가?
2. **일관성** — 다른 스펙이 이와 다르게 하면 아키텍처 일관성이 깨지는가?
3. **성격** — 특정 기능의 알고리즘/구현 선택이 아니라 기술 스택·컨벤션·정책 차원의 결정인가?

## 판단 신호 (Decision Signals)

위 세 기준은 추상적이라 매번 처음부터 판단하기 번거롭다. 아래 중 하나라도 해당하면 승격 후보로 보고 판단 절차를 따른다 — 신호가 하나도 없으면 대체로 승격 대상이 아니다.

- 공개 API(`public`/`protected` 시그니처, 어노테이션 계약 등 라이브러리 소비자에게 노출되는 것)가 바뀌는 결정
- 빌드 스크립트의 의존성 선언 방식·스코프 정책이 바뀌는 결정 (예: Version Catalog 도입, `api`/`implementation` 구분 기준)
- 여러 클래스·패키지에 걸쳐 있는 구조적 패턴(예외 처리 체계, 리플렉션 접근 방식 등)을 새로 도입하거나 바꾸는 결정
- 이미 2개 이상의 스펙에서 유사한 요구사항·제약이 반복 등장
- 다른 스펙이 이 결정을 암묵적 전제로 삼는 경우 — 명시해두지 않으면 다음 스펙 작성자가 같은 판단을 처음부터 다시 해야 한다
- 요구사항 문장에 "항상", "모든", "어떤 경우에도", "절대" 같은 전칭·부정 양화사가 등장 — 특정 스펙 하나의 범위를 넘어서는 전역 규칙일 가능성이 높다
- 대안이 명시적으로 검토되고 트레이드오프가 발생한 기술 선택(라이브러리·패턴 채택)

## 판단 절차

1. 이번 스펙의 requirements.md Constraints, design.md의 컴포넌트별 근거, Correctness Properties에서 나온 항목을 훑는다.
2. 각 항목에 위 세 기준과 판단 신호를 함께 적용한다. 하나도 해당 안 되면 승격하지 않고 이 스펙 문서에만 남긴다.
3. 애매해도 여기서 멈추지 않는다 — 판단 근거와 함께 tasks.md의 구체적인 서브태스크로 반영한다("관련 문서 업데이트" 태스크, `assets/tasks-template.md` 참고). 판단이 틀렸으면 tasks.md 승인 시 사용자가 검토하며 고친다.
4. 승격이 확정되면 성격에 따라 분류한다:
   - 강제 규칙(하지 말아야 할 것, 항상 성립해야 하는 동작) → `G-` (Global Rules)
   - 왜 그렇게 했는지에 대한 근거만 있고 강제할 규칙은 없음 → `D-` (Decision Log)
   - 둘 다 있음 → `G-`와 `D-`를 짝으로 만든다 (예: `G-2`/`D-2`처럼 번호를 맞추면 추적이 쉽다)
   - 2개 이상 스펙에서 반복 등장하는 용어 → Glossary

## CLAUDE.md와의 경계

일반적인 코드 스타일·네이밍 컨벤션(패키지 구조, 클래스 네이밍 등 코드를 보면 알 수 있는 것)은 baseline으로 승격하지 않는다 — CLAUDE.md의 몫이다. baseline은 코드만 봐서는 알 수 없는 "왜 이렇게 정했는가"와 "무엇을 하면 안 되는가"를 담는다.

## 예시

**승격하는 경우**
- "테스트 전용 의존성은 `testImplementation` 스코프로 격리한다" — 기준 1, 2 해당(모든 스펙에 적용되고, 어기면 라이브러리 소비자에게 불필요한 의존성이 노출된다).
- "Correctness Property 구현에는 jqwik을 쓴다" — 기준 3 해당(특정 기능이 아니라 테스트 전략 정책).

**승격하지 않는 경우**
- "이번 스펙에서는 Gradle 버전을 안 건드린다" — 이 스펙 하나의 범위 제한일 뿐, 다른 스펙에 적용할 원칙이 아니다 (`C-`로 그 스펙에만 남긴다).
- "이 컴포넌트는 캐시에 `ConcurrentHashMap`을 쓴다" — 특정 기능의 구현 선택이고 정책 차원이 아니다 (design.md의 컴포넌트별 근거로 충분하다).
